# PiContextLab 项目说明与展示路线

PiContextLab 是在开源 Pi Agent Core 1.6.0 上实现的上下文预算与工具选择改造，使用官方 DeepSeek API；PiMetricLab 是检验框架行为的经营指标调查应用。它属于个人开源工程项目。不同验证客户端、实验脚本和策略版本都归于同一项目。

## 解决的问题

Agent 接入的工具与返回结果增多后，问题不只是消息太长：模型看到的工具声明可能与恢复时允许执行的集合不同，多个工具结果可能共同挤满上下文，外置后又可能因为找不到字段或反复回读而耗尽额度。报告能封存也不代表金额、贡献组或解释正确。

本项目把这些问题拆成可检查的边界，并保留实际失败。没有把现有 BM25、哈希存储、压缩或持久化思想称作原创。

## 框架贡献与应用边界

| 部分 | 已实现 | 主要证据 |
|---|---|---|
| 原生策略接口 | 规范化 transcript 后，由 `ModelContextPolicy` 同时返回 provider 视图及允许执行的工具；核心核对声明和执行对象 | [策略接口](../vendor/pi-agent-core/src/model-context.ts)、[原版/派生版工程对照](../test/framework.test.ts) |
| 工具选择 | BM25 排名、完整依赖闭包、数量与 schema 双预算、按需发现；有界索引按当前元数据失效 | [路由实现](../vendor/pi-agent-core/src/tool-router.ts)、[固定 CPU 对照](../evidence/routing-cache/) |
| 上下文管理 | 路由后超限才外置；完整用户轮次打包，保护最近回读批次；按 SHA 保存精确来源，批量 JSON pointer 限量回读和续读 | [打包器](../vendor/pi-agent-core/src/context-budget.ts)、[精确回读](../vendor/pi-agent-core/src/context-artifacts.ts) |
| 空间与字段策略 | 有界校验反馈、共享回读预算、实际响应后的预算规划；可选完整 JSON 子树保留及数值字面保真 | [规划](../vendor/pi-agent-core/src/context-result-budget.ts)、[子树选择](../vendor/pi-agent-core/src/context-retention.ts)、[最新真实对照](../evidence/exact-retention/) |
| 应用可靠性 | owner/epoch 写入约束、未知调用占额度、请求/响应绑定、恢复；确定性指标和证据封存、结构化声明来源检查 | [宿主](../src/runtime.ts)、[持久状态](../src/store.ts)、[封存校验](../src/brief-proof.ts) |

Pi 上游已有 Agent 循环、工具执行、压缩和高层持久化能力。本项目改动的是派生核心的可选协议与预算组合；业务持久化、SQL、额度、报告与审核属于宿主，不混为新模型算法。

## 真实业务流程

```mermaid
flowchart LR
    A[有来源清单的订单CSV] --> B[不可变数据版本与指标口径]
    B --> C[明确指标和可比期间]
    C --> D[Pi / DeepSeek自主选择受限工具]
    D --> E[确定性计算与SQL来源证据]
    E --> F[封存报告与人工复核入口]
```

分析人员可以调查净额、正向销售、退货、订单、已识别客户与客单价，按国家或商品拆解变化，并回查 SQL、参数、数据版本、口径和结果哈希。输入不明确时先澄清。工具不接受任意 SQL、shell 或审批操作；完整 Web 工作台支持任务进度、取消、恢复、来源查看和离线 HTML 导出。

完整 UCI Online Retail 的 541,909 行入库后，用独立原 Excel Decimal/set 程序核对 12 个指标值、29 个国家分组及质量计数。结构化报告客户端还在同一封存事务中核对数值、方向、来源与贡献组；叙述、因果和数据真实性仍需另行判断，报告保持 Unreviewed。

## 哪些结果可以讲

- 当前核心和宿主有 101 项服务端工程测试，另有 14 项真实浏览器检查、完整 UCI 核对。工程通过证明对应边界，不等于模型效果或生产 SLA。
- 37,292 工具目录的固定 CPU 负载中，有界索引复用保持 16 组完整排名/分数/选集一致，路由中位耗时 991ms→433ms；每变体 16 次且包含冷启动，不是端到端 Agent 提速。
- 新结构化业务研究中，完整上下文两项事实核对通过；预算两项均未通过。错误的已封存声明随后成为来源校验的 CPU 回归，原模型评分未改。
- 最新部署来源审计实际调用 DeepSeek 12 次，四项均正确。开启精确保留后，一项回读路径由三条变一条，但各任务仍三次请求、一次回读，输入 token 更多，未证明效率收益。

[完整研究索引](validation.md)区分真实模型、脚本 provider、公开检索和工程控制。117 次已关闭真实生成请求来自不同任务，不能拼成同一个准确率分母；旧研究不重开或追加额度挑结果。

## 简历建议：作为一项项目写三条

技术栈：TypeScript、Pi Agent Core、DeepSeek API、BM25、SQLite、DuckDB。

1. 派生 Pi Agent Core，在模型请求边界同时约束上下文视图与本轮工具执行集合；实现依赖闭包、数量/schema 双预算和元数据失效的有界路由索引。
2. 实现保留权威历史的来源外置与完整轮次打包、精确 JSON pointer 续读、共享回读预算及响应后的空间规划；支持原始数值字面和可选结构化字段保留。
3. 构建经营指标验证应用，在完整 541,909 行公开数据上核对确定性金额与分组；以持久额度、写入归属、来源封存和真实 DeepSeek 对照验证工程边界，保留负效果结果。

系统岗位可用固定 CPU 路由测量替换一条；算法岗位保留检索对照和失败分析。项目没有训练新模型、生产客户或可信成功率增益。详细可替换写法与追问见[简历材料](resume.md)。

## 十分钟展示顺序

| 时间 | 操作 | 应解释的结论 |
|---|---|---|
| 0–2分钟 | 打开[真实经营报告](../evidence/structured-brief/study/autumn-return-offset-full.html)，查看指标、分组和证据 | 确定性结果和模型解释的分界；没有伪造人工审核 |
| 2–4分钟 | 阅读 `model-context.ts` 与 `agent-loop.ts` 的声明/执行检查 | 为什么少放几个工具描述不足以约束实际执行 |
| 4–6分钟 | 打开工作台的策略轨迹和 `store.ts` 请求绑定 | 完整上下文与预算策略的差异；未知调用为什么仍计额度 |
| 6–8分钟 | 看[最新真实轨迹分析](../evidence/exact-retention/study/trace-audit.json)及失败的业务预算报告 | 少读字段不必然少一次请求；引用合法不等于事实正确 |
| 8–10分钟 | 运行脚本控制或独立 SDK 集成控制，解释输出标记 | 工程控制不是模型准确率，也不是生产部署证明 |

没有服务环境时，公开 HTML、原始 JSON 和源码仍可用于讲解，但不要把阅读静态文件描述成现场重新运行了实验。有服务器时按根 README 准备独立环境；历史研究已关闭，展示不需要重新消耗模型额度。

## 交付范围

默认真实应用继续使用完整上下文，字段定位和精确保留默认关闭。当前是可信本机/内网的单租户工作台；没有公网鉴权、多租户隔离、支付写入或第三方副作用 exactly-once 承诺。Pi 上游固定版本的许可与哈希保留；原始研究克隆、个人主页和既有自动任务不因本项目更改。

建议学习顺序：[本说明](project-brief.md) → [接入与运行](../README.md#运行) → [完整讲解](handbook.md) → [框架实现](framework.md) → [原始验证](validation.md)。先独立跑通、核查并能解释源码，再用于投递。

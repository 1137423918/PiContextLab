# v4 真实 API 对照：运行前方案

本方案新增六月/七月正向销售额调查及六字段溯源审计。它不重跑已关闭的 v1/v2 报告、旧问题或 8 条 CPU 字段定位诊断。目标是验证当前框架是否能用真实 DeepSeek 完成原文恢复，并测量跨轮次开销；不提前假设字段搜索有效。

## 业务源与校验

完整 UCI 数据保持只读。新任务比较 gross_sales：基期 `[2011-06-01,2011-07-01)`、本期 `[2011-07-01,2011-08-01)`，calendar_month，country Top5＋OTHER，并封存报告。另运行新的中文模糊问题，检查澄清与零查询证据。

审计只使用第一任务的新报告。开始前验证任务 completed、匹配的指标/日期/country/Top5、证据数据集和口径、结果 SHA256 及证据身份。缺失或不匹配时停止审计，不使用旧报告、人工补报告或再请求模型争取成功。

六个字段：dataset_id、metric、dimension、baseline_start、current_end、breakdown_result_sha256。前五项较容易，最后一项要求获得对应证据的精确校验和；不能把这个复制/检索诊断说成复杂经营推理准确率。当前问题没有注入预期答案字典，源历史自然包含所需事实。

## 对照

| 变体 | 历史与工具 |
|---|---|
| upstream-full | 独立 npm Pi1.6.0，全量内容历史，不添加原文工具 |
| native-read | 当前 core4，16KiB 预算、精确回读，字段定位关闭 |
| native-search | 相同 core4 与预算，字段定位开启 |

每个变体复制相同初始历史并记录输入内容哈希，显示用 details 统一移除。案例一直接审计；案例二插入六轮预先固定的 MIT 上游 README 摘录。这些是受控上下文，不是真实客户对话。

案例一顺序为 full/read/search，案例二为 search/read/full。不作随机化或独立重复，缓存和供应商后端可能影响延迟/费用。read 与 search 除选项外配置相同，但新增 schema 会占用预算并改变可保留历史；对照测的是完整选项的影响，不是纯检索算法收益。

## 额度和评分

- 业务最多 9 次请求，输出上限合计 7,680 tokens；审计六次变体运行，每次最多 4 请求、单次输出最多 768，总计最多 24 请求与 18,432 输出 tokens。
- 总上限 **33 请求 / 26,112 输出 tokens**，完整响应 deadline 90 秒，适配器重试 0。外壳另有资源/总时长上限，可能在请求额度用完前中止。
- 官方 DeepSeek Flash，thinking disabled，temperature0；native 上下文 JSON 16,384 字节、inline 阈值 2,048、工具上限2、schema4,096；所有变体外层 JSON 上限65,536。
- 六字段必须逐项等于新报告源字符串，且 stopReason 为 stop。允许多余键与单个外层 JSON 代码围栏；不修复其他散文、null、漏项或错误值。
- 每个案例/变体只运行一次，失败、额度耗尽和 unknown 都保留，不续跑挑分。每个变体后原子保存 checkpoint，SQLite 账本保留未决尝试。
- 记录全部请求累计输入 tokens（含缓存）、输出、估计费用、时间、每轮规范化 JSON 与 wire 大小、工具调用和完整失败。估计费用不是账单，未知请求不能按零支出推断。

## 可以和不可以得出的结论

能观察当前 DeepSeek 配置上的有限集成行为、检索路径和成本。两个审计案例共享一个源报告与目标字段，不能当作独立随机任务计算普遍成功率，也不能据此证明统计显著、跨模型泛化或企业收益。

本次基线不添加没有 artifact 的 utility schema，与旧研究的设置不同；报告、字段、问题也不同，**不能直接比较 v1/v2 与 v4 分数作为版本提升曲线**。旧结果原样保留。只有本次相同源、模型和方案内的变体可以逐例比较。

# 简历与面试材料

项目名：**PiContextLab — Pi Agent Core 上下文预算与工具选择改造**。个人开源工程项目；PiMetricLab 是真实数据验证客户端，不拆成两个相互独立的履历成果。

## 算法与 Agent 框架方向：可直接使用

技术栈：TypeScript、Pi Agent Core、DeepSeek API、BM25、DuckDB、SQLite。

- 基于 Pi 1.6.0 派生 Agent Core，新增请求级 `ModelContextPolicy`，将模型可见工具声明与本轮执行白名单绑定；实现工具依赖闭包、数量/schema 双预算选择和漏召回发现，将工具集合与请求及响应身份持久绑定，恢复时拒绝未绑定调用。
- 实现按完整 user turn 打包的上下文策略，将大工具结果按 SHA256 外置并保留来源身份，支持会话隔离、完整性校验和批量 JSON pointer 限量回查；保留权威历史，预算不足时在请求前拒绝。
- 构建原版/最近窗口/改造核心的 DeepSeek API 小样本对照，以及 101 条公开查询对 37,292 个工具的检索评测，记录任务结果、累计 token、schema 开销和失败轨迹；根据身份混淆、分页耗尽及批量路径错误完善接口。

这版强调实际实现与评估工作。**没有可信召回/成功率提升，不能添加“提升 XX%”“新算法 SOTA”“无损推理”等表述。** BM25 是使用的已有算法；工具检索不是权限系统。

## 两分钟讲解

“我选择了 Pi 轻量 core 做改造。Agent 的工具和上下文越来越多时，单纯裁 prompt 不能保证实际执行集合一致。我在规范化 transcript 与 provider 请求之间加了一个策略接口，同时返回上下文视图和可执行工具，核心核对它们，宿主保存轮次选择用于恢复。

“策略包含两个部分：工具以词法排名和依赖闭包在双预算内选择；上下文将大结果外置成可校验 artifact，旧历史按完整用户轮次装入，当前要求不截断。模型能按多个 JSON 路径限量取原文。业务验证用完整公开零售数据，金额由确定性程序计算。

“实验没有得到普遍提升。公开目录中字段化文档比完整文档召回差；DeepSeek 的压缩方案会混淆存储身份、猜错路径和耗尽额度。我保留这些结果，修复了批量读取中单路径错误导致全部字段丢失的问题。项目的主要成果是可运行的框架接口、执行约束和可复现的评估体系，效果优化仍需要独立评测。”

## 需要能回答的追问

**为什么改 core？** 需要让声明、执行和恢复同属一轮；只在模型消息里少放几个工具不足以保证执行集合。可以在宿主另写 wrapper，但本项目在核心加可选协议，默认路径保持原版。

**预算是 token 吗？** 是上下文 JSON 字节及工具 schema 字节，实际 tokens 来自供应商 usage 并累计所有轮次。减少第一轮字节可能增加 recall 次数，最终成本反而更高。

**外置无损吗？** 精确存储原文、校验可回读，不代表模型任务无损。缺乏语义、路径提示不足和额度消耗都会失败。

**公开评测有多强？** 只做 ToolRet API-Bank101 查询和 web37292 工具，属于公开子集，未训练、未用 positive labels 排名、未调参刷分。字段化 R@10 20.13%，低于完整文档30.94%。

**成功率提升多少？** 当前没有可以报告的提升。两轮 API 审计每种策略只有两个案例，不能推导总体准确率。v3 工程修复通过控制回归，尚无真实 API 复测成绩。

**恢复 exactly-once 吗？** 不保证第三方副作用。只读计算可重放，证据与工具结果原子提交，报告按身份幂等，unknown 请求仍占额度。

**与 Pi 已有能力有什么区别？** Pi 已有工具执行、transformContext、压缩和持久化 Harness。新增的是本项目 core 策略接口、声明/执行约束、预算组合和配套评估，不把既有能力当原创。

**下一步怎样研究？** 在未使用过的独立任务上比较完整文档检索、预算目标和可回查结构；先冻结方案，再做重复和错误分类。v1/v2 已关闭，不反复重跑挑成功。路线图不写作成果。
